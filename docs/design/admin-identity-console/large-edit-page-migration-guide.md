# 大型编辑页改造指南

本文档总结组织编辑页改造过程中的稳定结论，供后续应用、用户、Provider 等复杂编辑页迁移时参考。它不是新的视觉系统，具体实现仍以 `DESIGN.md`、`web-admin/AGENTS.md`、Ant Design 和现有代码风格为准。

## 适用范围

适用于字段多、分组多、保存链路复杂、需要 tabs 的后台编辑页。简单弹窗、短表单、只读详情页不需要套用完整壳层。

组织编辑页当前作为样板，稳定结构为：

- 顶部对象栏：返回、路径、对象标题、未保存状态。
- Tabs：基础 / 品牌 / 登录安全 / 导航菜单 / 账号资料 / 多因素认证 / 目录服务。
- 正文：独立滚动，按区块标题、表单网格、表格模块组织。
- 底部操作栏：固定在编辑壳底部，按钮顺序为取消 / 保存 / 保存并返回。

## 迁移原则

- 先统一编辑页壳，再迁移字段细节。不要在每个业务页重复发明返回、tabs、底部保存栏、脏数据确认和保存前校验。
- 页面要像后台配置工具，不像介绍页。正文保持紧凑，避免 hero、大卡片、营销式说明和装饰性背景。
- 标题、表单、表格和提示信息要形成稳定网格。区块标题使用统一左边界；内容可按场景收窄，但标题不要跟着漂移。
- 用户可见文案必须走 i18n；中英文都要能显示完整，不能只按中文截图调宽度。
- 明暗主题都要验收。新增颜色优先使用现有 token 或 `--admin-shell-*` 变量，避免白底、浅灰、硬编码蓝色在暗色主题失效。

## 页面壳约定

大型编辑页推荐复用以下结构：

```text
EditPage
  Header: Back / Breadcrumb / Title / Dirty state
  Tabs
  ScrollContent
    ActiveTabContent
  FixedFooter: Cancel / Save / Save and return
```

关键行为：

- 返回和取消都要经过脏数据确认。
- 保存中禁用重复提交，主保存按钮显示 loading。
- 保存前做前端必填校验，并切回第一个错误所在 tab。
- tab key 应写入 hash，刷新或返回后能恢复当前 tab。
- 子资源如果是即时生效，不应触发组织页脏数据状态。

## 正文布局规则

- 正文水平内边距保持统一，桌面端优先 32px。
- 区块标题使用 14px medium，带轻量左侧主色竖线。
- 表单标签、输入值、表格内容、按钮文字优先 12px，避免和 AntD 默认 14px 混用。
- 两列表单使用固定标签宽度和 `minmax` 网格；长字段、语言、标签、URL 等使用整行。
- 数字字段使用 `InputNumber`，内容右对齐；同一区块数字控件宽度要一致。
- 禁用字段必须解释原因，使用 Tooltip 或靠近字段的说明文本。
- 长 URL、资源路径、内部标识要有 tooltip、复制或打开能力，不能只截断。

## 表格模块规则

表格型配置使用统一的轻量表格模块：

- 表格标题放在表格 title/toolbar 左侧，操作按钮放右侧。
- 标题字号和正文保持克制，通常 12px、500 字重即可。
- 表格宽度按信息量控制，不默认全屏铺开。
- 列很多的配置表可以保留表内横向滚动，但行内操作列应固定在右侧，避免管理员需要先横向滚动才能找到上移、下移、删除等常用操作。
- 操作列的 icon-only 按钮必须有 Tooltip 和 `aria-label`。
- 删除、移除类动作必须有确认；如果底部保存才生效，文案用“移除”比“删除”更准确。
- 禁用按钮必须说明原因，例如“最多支持 4 种认证方式，移除后可继续添加”。
- 空态文字要具体，避免只显示空白表格。

## Tab 级经验

### 基础

- 基础信息适合两列；主页地址、语言、标签集合适合整行。
- 默认应用无可选项时，应禁用 Select 并给 Tooltip 说明“暂无可选应用，新增应用后可选择”。
- 用户余额这类汇总字段应只读展示，并说明不能在组织编辑页直接修改。
- 语言多选高度会自然变高，放整行比塞进右列更稳。

### 品牌

- 品牌资产用“输入框 + 预览图 + 状态 + 查看”结构。状态文案要短，例如“使用默认”“已配置”。
- 暗色 Logo 开关应靠近 Logo 资源配置，不要孤立在区块顶部。
- 主题模式用分段按钮即可；全局主题说明应是轻量说明文本，不要做成禁用输入框或厚重提示框。
- 资源预览列要留出状态和查看按钮的宽度，避免出现状态截断。

### 登录安全

- 密码、万能密码、验证码、IP 白名单等敏感字段需要明确说明用途和风险。
- `0`、空值、禁用等特殊语义要写在 placeholder 或 Tooltip 中。
- 长标签不能撑乱全局表单，必要时只在编辑页局部收窄字号和标签换行。

### 导航菜单

- 多棵树适合左右并列面板，并在标题区显示已选数量。
- 树节点和 checkbox 要保持稳定 key，不能用不稳定 index。
- 账号菜单这种窄控件不要跟着全宽拉伸，控制在合理宽度。

### 账号资料

- “字段”不如“账号资料”清晰；表格列标题用“属性”。
- 仅中文或仅英文都不够稳，建议展示为 `显示名称（Display name）`。内部保存值仍使用英文枚举。
- 筛选、搜索、可见/可编辑状态要放在表格工具栏，保持和表格语义绑定。

### 多因素认证

- 区块标题必须和其它 tab 左边界一致；只让时长字段和表格进入窄容器。
- 表格宽度控制在可扫描范围，不要全屏铺开。
- 认证方式顺序有业务含义时，标题旁 info 要说明“按从上到下顺序展示/验证”。
- 达到上限时禁用添加，并提供 Tooltip。
- 上移、下移、删除需要 Tooltip、`aria-label` 和确认。

### 目录服务

- LDAP 服务器是独立资源，添加、编辑、删除、同步等即时生效操作要明确提示，不受底部保存/取消控制。
- LDAP 表格不应全屏铺开，宽度按列信息量收敛。
- LDAP 属性下拉宽度应受控，单字段不需要横跨整页。
- Kerberos 表单可以两列输入 + 大文本域，但 `keytab` 是否应该是上传文件需要按业务再确认。
- 表格状态避免中英混杂，例如 `Disable` 应本地化为“禁用”。

### 应用

- 应用编辑页属于多 tab 大编辑页，和组织、用户更接近，不应套用群组、角色这类单页正文形态。
- 应用页正文可以保留业务 tab 的原始语义，但壳层必须复用同一套返回、路径、tabs、滚动正文和底部操作栏。
- OIDC/OAuth、SAML、Provider 绑定、Reverse Proxy 这类宽配置表优先保证列语义和可读性。必要时保留表内横向滚动，不要为了消除横滚强行压缩列宽。
- 通用 URL 表如果复用于不同业务字段，要允许覆盖列名。`其他域名` 不应继续显示“重定向 URL”这种来自 Redirect URI 场景的列名。
- 界面定制 tab 不要直接嵌入有登录、授权或 Prompt 副作用的运行时页面作为预览。编辑页内优先使用静态只读预览，避免触发 OAuthWidget、登录态检查、callback 或白屏。
- 应用页里的技术专有名词可以保留英文，例如 `OIDC/OAuth`、`SAML`、`Reverse Proxy`、`Token`、`Client`；但 `Other domains`、`Upstream host`、`SSL cert` 这类后台字段仍应补齐 zh/en locale，不能落成占位英文。
- Provider 目标组织、允许组织、API 映射等字段有真实认证语义。样式迁移只整理呈现和校验定位，不顺手改变保存 payload 或运行时解析规则。
- Provider logo 可能是透明底深色图标，暗色表格内需要浅色徽标容器或等价 fallback；不要直接渲染空 `src` 或让黑色图标贴在暗色单元格上。

## 已踩坑

- Tooltip 包住禁用控件后，控件可能塌宽。需要 wrapper `display: block; width: 100%`，并给内部 Select/InputNumber 显式宽度。
- 不要把区块标题包进窄容器。MFA 页曾出现标题左边界和其它 tab 不一致的问题。
- 表格标题栏和表格边框容易形成双线。表格 title、thead、container 的 border 要统一。
- 视觉上收窄表格是对的，但如果标题、表单和表格各自居中，会形成“小岛”。应先统一左边界，再控制最大宽度。
- 暗色主题不能只看白天模式。浅底标题栏、禁用输入框、提示框和表格边框都要在暗色模式下检查。
- 一些表格内操作是即时生效，不依赖全局保存。必须在 UI 上说明，否则用户点取消后会误以为数据回滚。
- 本地 7004 dev server 可能残留旧 bundle。刷新无变化时先检查 bundle 字符串或重启本地前端代理，不要误判代码未生效。

## 可复用与不宜抽象

建议优先沉淀：

- 编辑页壳：Header / Tabs / ScrollContent / Footer。
- 区块标题、表单行、必填标识、错误展示。
- 固定底部操作栏和脏数据确认。
- 表格标题工具栏、空态、操作 Tooltip/aria 模式。
- 保存前校验并跳回错误 tab 的机制。

暂不急于抽象：

- 单个业务字段的布局规则。
- LDAP、MFA、账号资料等业务表格的内部列定义。
- 某个页面临时宽度和特殊状态文案。

抽象边界以“能被至少两个编辑页稳定复用”为准，不为了当前页面好看而制造公共组件负担。

## 后续页面迁移约定

后续继续改造 Provider、Syncer、证书、密钥等编辑页时，先沿用当前编辑页 contract，不要先做新的视觉抽象。

### 壳层 contract

- 多 tab 或大型编辑页使用 `admin-large-edit-page xxx-edit-page` 作为页面根节点，并复用 `LargeEditShell`。
- `LargeEditShell` 只负责公共壳：顶部返回/路径/标题/脏状态、tabs 插槽、滚动正文、底部操作栏。
- 页面正文仍由业务页自己控制。多 tab 和单 tab 的差异应该主要留在正文区域，不要影响公共头部和底部。
- 单 tab 身份对象页继续使用 `identity-object-edit-page xxx-edit-page` 这类作用域，不必强行改成多 tab 结构。
- 老式短表单可以先接入 `admin-access-edit-page` / `admin-identity-object-edit-page` 的兼容样式，等页面价值足够再迁移到完整壳层。

### 单 tab 与多 tab 边界

当前稳定边界如下：

- 多 tab 编辑页：组织、用户、应用。它们有多个相对独立的配置域，适合显示 tabs，并通过 hash 记住当前 tab。
- 单 tab 编辑页：群组、角色。它们字段和表格较少，适合直接在正文中分区，不需要为了形式统一渲染一个“单独 tab”。
- 两类页面应共用同一套编辑壳：返回、路径、标题、脏状态、滚动正文和底部操作栏一致。
- 两类页面的差异只体现在 `LargeEditShell` 的 `tabs` 插槽是否传入，以及正文内部是 tab 面板还是单页分区。
- 如果单 tab 页面后续增长为多 tab，优先保留原页面根 class 和 `classPrefix`，新增 tabs/hash 行为；不要因为升级为多 tab 重命名已有 selector。
- 如果多 tab 页面某个 tab 只有少量字段，也不要拆成新的壳。tab 内部可以用 section 或 item class 做局部收敛。

### 样式边界

- `web-admin/src/App.less` 只做后台样式顶层聚合入口，按顺序引入全局 shell、身份控制台页面、列表页、编辑页、响应式规则和登录页模块。不要把新页面的大段样式直接写回 `App.less`。
- `web-admin/src/styles/identity-console-pages.less` 是身份控制台和相关后台工作页的聚合入口；页面族样式放入 `web-admin/src/styles/identity/`，例如概览/共享控制台、Server Store、应用接入、审计治理、组织同步、系统信息、平台运维和证据链。
- `web-admin/src/styles/list-pages.less` 是列表页样式聚合入口；公共列表壳、组织/用户类列表、应用/Provider 类列表、查询工具栏分别放入 `web-admin/src/styles/list/`。
- `web-admin/src/styles/large-edit-pages.less` 是大型编辑页样式聚合入口；公共编辑壳和 mixin 放在 `web-admin/src/styles/edit/large-edit-common.less`，页面私有正文样式放在 `web-admin/src/styles/edit/` 下对应业务模块。
- 不要为了“公共文件里不能有业务 selector”而重命名 `.organization-edit-page`、`.user-edit-page` 等类名。它们是页面作用域边界，能防止 AntD 覆盖样式外溢。
- 新增页面正文样式必须挂在 `.xxx-edit-page` 下；避免裸写 `.ant-form-item`、`.ant-table`、`.ant-btn`。
- 样式入口文件只维护 import 顺序和页面族归属。除非明确需要改变视觉，否则迁移页面时不要顺手调整颜色、字号、间距、按钮尺寸或表格密度。
- 已迁移编辑页挂到 `admin-shell-route-scroll-without-card` 时，`padding: 0` 和页面根节点 `flex: 1 1 auto` 属于公共壳层挂载 contract，后续新增页面应并入同一组 selector，不要每页复制一段。
- tab 正文里可稳定复用的呈现骨架应优先挂公共 class：`admin-large-edit-form-content`、`admin-large-edit-content-section-title`、`admin-large-edit-full-width-row`、`admin-large-edit-form-content .ant-table-*` 和 `admin-large-edit-form-content .ant-btn-sm`。页面私有 class 只补业务特例。
- 字段 label、legacy Row/Col 首列 label、单 tab 身份对象页 label 统一引用 `--admin-large-edit-label-color`；不要在新迁移页里重新硬编码深灰或次级灰，避免组织、用户、应用、群组、角色、权限之间出现黑/灰不一致。
- 页面 root、card、card body、移动端 root/card、暗色表单控件状态、字段 grid、字段 row、宽字段 row、section 标题、标题 marker、字段 label、必填星号、冒号、字段 control、字段错误、legacy Row/Col 首列 label 这类同语义同视觉原子应通过 `admin-large-edit-*-base()` LESS mixin 收敛，并保留页面 selector 作为作用域边界。
- 表格标题工具栏、标题文字、标题帮助图标、focus ring、toolbar 小按钮、行内小操作按钮和 icon-only 操作按钮也属于可复用样式原子，应优先使用 `admin-large-edit-table-*` / `admin-large-edit-*-action-*` mixin；业务列宽、树、LDAP、账号资料等内部结构继续保留页面局部样式。
- 特例布局优先使用 section 或 item 级 class，例如 `user-edit-section-password-authentication`，不要把单个字段问题升级成全局规则。
- 组织 LDAP、导航树、应用静态预览、账号资料表格、权限规则表格等业务特例不要硬抽成公共 mixin 或公共组件；后续只有当 2-3 个新迁移页面出现稳定重复时，再抽新的公共变量、mixin 或组件。已有公共正文 class 可以直接复用，不需要每个页面重新微调。

### 迁移步骤建议

1. 先接入页面根 class、`LargeEditShell`、底部操作栏和脏数据确认，确保壳层行为一致。
2. 再迁移 tabs 或单 tab 正文，先保留原字段语义和保存 payload，不在样式迁移中顺手改业务。
3. 给页面正文建立 `.xxx-edit-page` 作用域，并优先挂公共正文 class，迁移表单网格、区块标题、表格 toolbar 和移动端规则。
4. 对表格模块统一处理标题、右上操作、空态、行内小按钮、Tooltip、`aria-label` 和删除确认。
5. 用浏览器检查每个 tab 的首屏、滚动尾部、空态、长文本、禁用态和暗色主题；发现页面特例时先写局部 class。
6. 最后再评估是否有真实重复值得沉淀为公共配置。

### 不建议现在做的优化

- 不建议绕过聚合入口从 `App.less` 直接引入某个业务页子模块；入口文件负责稳定 cascade，业务页只维护自己的模块。
- 不建议把页面私有模块继续拆到单字段、单表格或单组件粒度，除非该页面域已经大到影响定位，并且存在清晰的二级页面族边界。
- 不建议把组织、用户、群组、角色的正文网格强行抽成同一个公共组件。它们的字段密度、表格比例和业务交互差异较大。
- 不建议为了减少 CSS 行数牺牲作用域清晰度。后台编辑页更需要可预测的局部覆盖和可回归验证。
- 不建议把视觉 smoke 截图、临时 Playwright 输出、本地 dev 日志写入仓库。

## 验收清单

每个编辑页迁移完成后至少检查：

- 所有 tabs 可切换，hash 刷新后能恢复当前 tab。
- 返回、取消、保存、保存并返回都可用，脏数据确认语义正确。
- 必填校验能在前端拦截，并定位到对应 tab。
- 明暗主题下表单、表格、禁用态、提示、底部栏都可读。
- 中英文文案都存在，长文本不撑破布局。
- 表格有稳定 `rowKey`，操作按钮有 Tooltip 和 `aria-label`。
- 即时生效子资源有明确提示，不误导用户依赖底部保存。
- 页面没有横向溢出，固定底部栏不遮挡正文关键内容。

建议验证命令：

```powershell
cd web-admin
bun run test -- src/OrganizationEditPage.test.tsx --watchAll=false --runInBand
bun run typecheck --pretty false
cd ..
git diff --check
```

如果改动涉及表格组件，也要运行对应表格测试。若改动涉及真实运行态视觉，应使用本地前端代理 60 测试后台做浏览器 smoke，并分别检查浅色/暗色主题。

- 不要提交截图、临时设计稿、本地预览图片、dev server 日志或浏览器录制产物。
- 本轮组织编辑页改造过程中出现的剪贴板图片、本地预览图片和本地 log 只用于讨论和验证，不应进入 git。
- 文档应记录可复用规则，不记录一次性会话过程、截图路径、私有后台地址、登录凭据、账号或测试环境敏感信息。
