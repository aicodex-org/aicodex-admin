## Context

`aicodex-admin` 当前已经具备 Casdoor 用户、组织、用户组和企业微信登录能力。企业微信登录解决的是“用户如何进入认证中心”，但没有解决“企业微信通讯录中的部门、成员、部门负责人、直属上级关系如何成为本地身份和权限范围的依据”。

现有模型可以承接首版能力：

- `Group` 已有 `Owner`、`Name`、`DisplayName`、`Manager`、`Type`、`ParentId`、`IsTopGroup`、`IsEnabled`，适合承载企业微信部门树。
- `User` 已有 `Owner`、`Name`、`ExternalId`、`Wecom`、`Email`、`Phone`、`Title`、`Avatar`、`Groups`、`Properties`，适合承载企业微信成员和外部标识。
- 现有 `Syncer` 主要面向数据库用户同步，提供了同步任务和错误展示思路，但它的字段和执行逻辑与企业微信通讯录 API 不匹配。

本次变更的下游使用者包括：

- `aicodex-admin` 后台管理员：配置通讯录同步、手动执行同步、查看同步结果。
- `aicodex-api`：后续通过统一认证和稳定用户映射识别 AI 使用者。
- `aicodex-insight`：后续通过当前用户可管理范围过滤部门和直属/间接下属 AI 用量。

## Goals / Non-Goals

Goals:

- 为每个目标组织提供一套企业微信通讯录同步配置。
- 手动触发全量差异同步企业微信部门、成员、部门负责人、直属上级和成员部门关系。
- 将企业微信部门映射到 `Group`，将企业微信成员映射到 `User`，将成员部门关系映射到现有用户组关系。
- 同步企业微信成员的直属上级关系，为“查看自己下属 AI 使用额度”提供汇报链路依据。
- 提供同步执行记录、状态、统计和脱敏错误摘要。
- 提供当前用户可管理范围接口，供后续 `aicodex-insight` 做后端权限过滤。

Non-Goals:

- 不在第一版实现完整 dry-run 预览。
- 不在第一版实现企业微信回调事件增量同步。
- 不在第一版实现自动定时同步；可以在模型和任务入口上保留扩展点。
- 不在第一版实现“清空本地组织数据后重建”的覆盖式同步。
- 不把现有通用数据库 `Syncer` 改造成企业微信同步器。
- 不在本次变更中实现 `aicodex-api` 登录迁移或 `aicodex-insight` 报表功能。
- 不在第一版做复杂的多企业微信 Corp 同步到同一个本地组织的场景。
- 不把企业微信普通成员同步到 `built-in` 系统内置组织。

## Decisions

### 1. 新增专用企业微信组织同步模块，而不是复用数据库 Syncer

企业微信组织同步需要处理 `access_token`、通讯录权限、部门树、成员分页、成员状态、负责人关系、软禁用和外部 API 错误映射。现有 `Syncer` 的配置字段围绕数据库连接、表、列映射和 SSH，直接扩展会让数据库同步器承担不相关职责。

采用专用模块：

- 新增企业微信组织同步配置模型 `WecomOrganizationSyncConfig`。
- 新增企业微信组织同步执行记录模型 `WecomOrganizationSyncRun`。
- 新增企业微信部门映射、成员映射、成员部门、部门负责人、直属上级 5 类数据模型。
- 新增企业微信通讯录客户端和同步编排逻辑。
- 新增或扩展后台页面，支持配置、连接测试、手动同步和执行记录查看。

备选方案是给 `Syncer.Type` 增加 `WeCom` 分支。该方案能复用列表和定时任务结构，但会引入大量空字段和条件逻辑，不采用。

### 2. 本地数据模型采用“核心对象 + 映射表 + 关系表”

`Group` 和 `User` 继续作为 `aicodex-admin` 的核心身份对象。企业微信同步只维护外部来源映射和组织关系，不大规模侵入核心模型。

首版新增 7 张企业微信组织同步专用表：

- `wecom_organization_sync_config`
- `wecom_organization_sync_run`
- `wecom_department_mapping`
- `wecom_user_mapping`
- `wecom_user_department`
- `wecom_department_leader`
- `wecom_user_direct_leader`

设计原则：

- `Group` 保存企业微信部门树的本地展示和兼容字段。
- `User` 保存企业微信成员的本地身份对象。
- 映射表保存企业微信稳定 ID 与本地 `Owner + Name` 的绑定。
- 关系表保存参与权限计算的多对多关系，避免使用 `mediumtext` 数组承载核心 ids。
- `owner` 必须等于目标 `organization`；引用本地 `User` / `Group` 时仍显式保存 `user_owner`、`group_owner`、`leader_user_owner` 等字段。

详细字段见 [schema-design.md](./schema-design.md)。

### 3. 数据来源只基于企业微信公开 API，不假设内部表结构

企业微信通讯录的内部数据库表和字段不是公开契约，本次同步不能假设“企业微信组织架构表”存在，也不能依赖未公开字段。同步模块只面向企业微信公开通讯录 API 返回的数据建模。

首版必须能从企业微信公开接口获得并规范化以下字段：

- 部门：`id`、`parentid`、`name`、`order`、`department_leader`。
- 成员：`userid`、`department`、`main_department`、`is_leader_in_dept`、`direct_leader`、`status`，以及可用的展示和联系方式字段。

实现时不应把服务层绑定死在单个接口路径上。企业微信客户端应封装“部门快照”和“成员快照”能力，对同步服务输出统一的规范化快照。成员快照优先使用 `user/list_id + user/get`，当自建应用对 `user/list_id` 返回 `48002` 时，可回退到按部门读取成员详情的 `user/list`。连接测试也应校验自建应用 Secret 是否具备获取部门负责人和直属上级等关键字段的权限。

### 4. 第一版采用手动全量差异同步，后续再加定时和事件增量

手动全量同步更适合首版验收：

- 管理员可以在配置完成后明确触发同步。
- 首次接入时便于观察字段映射和错误明细。
- 不需要一开始处理企业微信事件回调验签、重试、乱序、幂等等额外复杂度。

本次“全量同步”不是清空重建，而是：

1. 从企业微信完整拉取当前权限范围内的部门、成员、部门负责人、直属上级和成员部门关系。
2. 基于企业微信稳定 ID 与本地映射做差异计算。
3. 对新增对象执行插入。
4. 对已存在对象更新展示字段、父子关系、成员关系、负责人关系、直属上级关系和状态字段。
5. 对本次完整成功结果中缺失的历史同步对象执行软禁用。

如果企业微信 API 调用、分页/递归拉取、数据规范化或本地落库中途失败，本次同步不得执行缺失对象软禁用。

详细算法见 [sync-algorithm.md](./sync-algorithm.md)。

### 5. 部门映射到 Group，成员映射到 User，权限关系独立保存

部门映射规则：

- `Group.Owner` 使用目标组织。
- `Group.Name` 使用稳定生成值，例如 `wecom-dept-<corp_id>-<department_id>`；由于现有 `Group.Name` 存在全局唯一约束，新建企业微信部门组必须包含企业 ID 以避免跨组织碰撞。
- `Group.DisplayName` 使用企业微信部门名称。
- `Group.ParentId` 使用父部门对应的本地 `Group.Name`。
- `Group.Type` 使用 `wecom-department`。
- `Group.Manager` 只保存主负责人对应的本地用户标识，用于兼容展示。
- 企业微信完整负责人列表保存到 `wecom_department_leader`，管理范围计算不得依赖 `Group.Manager`。

成员映射规则：

- 首先用目标组织 + 企业微信 `userid` 匹配已绑定用户，匹配字段优先级为 `User.Wecom`、`User.ExternalId`、扩展属性中的 `wecomUserId`。
- 已绑定用户同步时不修改 `User.Name`。
- 新建用户时使用企业微信 `userid` 生成稳定 `User.Name`，并处理非法字符和大小写策略。
- `User.Wecom` 保存企业微信 `userid`。
- 完整外部标识保存到 `wecom_user_mapping.external_id`。现有 `User.ExternalId` 长度为 `varchar(100)`，只有当 `wecom:<corp_id>:<userid>` 不超过长度限制时才可直接写入；否则写入长度受控 hash。
- 头像、手机号、邮箱等敏感资料字段只有在企业微信本次返回非空值时才更新；如果字段因权限限制未返回，组织同步不得清空已由 OAuth 登录或人事主数据回填的本地资料。
- `User.Groups` 只增删企业微信来源部门组，不覆盖或删除用户已有的手工用户组、角色相关组或其他来源组。

关系口径：

- 部门负责人来自 `department_leader` 或 `is_leader_in_dept`，落到 `wecom_department_leader`。
- 成员部门关系来自 `department` / `main_department`，落到 `wecom_user_department`。
- 直属上级来自 `direct_leader`，落到 `wecom_user_direct_leader`。
- 通讯录展示层级只表示部门树和成员归属，不用于推断直属上级或部门负责人。

### 6. 当前用户可管理范围由后端计算和输出

`aicodex-insight` 不能只依赖前端隐藏数据来控制权限范围。`aicodex-admin` 应提供后端接口，根据当前登录用户、部门负责人关系、直属上级关系和组织树计算可管理范围。

首版范围规则：

- 全局管理员或组织管理员可以查看整个目标组织范围。
- 普通用户如果是某个企业微信部门负责人，可以管理该部门及其子部门。
- 企业微信部门存在多个负责人时，所有负责人都应获得该部门及其子部门的管理范围。
- 普通用户如果是某些成员的直属上级，可以查看这些直接下属及递归下级成员的范围。
- 普通用户如果既不是部门负责人，也没有直属/间接下属，只返回本人范围。
- 接口返回可管理部门、可见用户稳定标识和用于下游系统过滤的外部用户 ID。

API 和响应契约见 [api-design.md](./api-design.md)。

### 7. 配置与密钥处理沿用后台敏感字段习惯

企业微信同步需要 `corp_id` 和自建应用 Secret。Secret 保存时应按项目现有敏感字段方式处理，前端回显时必须脱敏，更新时支持保留原密钥。

如果企业微信登录 Provider 已经配置过 `CorpId`、`AgentId`、`Secret`，本次同步可以允许管理员选择复用登录配置中的企业 ID；同步 Secret 应来自可读取通讯录详情的自建应用，且应用可见范围必须覆盖待同步部门和成员。不要使用“管理工具 > 通讯录同步”的 Secret 做读取型同步；该 Secret 在新增 IP 下只能稳定用于写入或 ID 比对，读取详情可能返回 `48009 api forbidden for contact assistant`。

### 8. 企业微信 Corp ID 绑定独立业务组织，禁止同步到 built-in

`built-in` 是系统内置管理组织。当前代码中 `User.Owner == "built-in"` 会被视为全局管理员，因此企业微信普通员工不能同步到 `built-in`。

推荐绑定规则：

- `Organization.Owner = admin`。
- `Organization.Name = wecom-<CorpID短码>`，作为稳定 ASCII 组织标识。
- `Organization.DisplayName` 首次创建时可用 `WeCom <CorpID短码>` 兜底，成功拉取企业微信完整快照后更新为根部门名称或企业显示名。
- `Organization.DefaultApplication = app-wecom-<CorpID短码>`，同步初始化时创建同名默认应用，作为同步用户编辑、登录和后续企业微信 Provider 配置的应用上下文。
- 后台手工上传同步用户头像时，应使用该用户所属应用选择 Storage Provider；如果 `app-wecom-*` 未绑定 Storage Provider，应提示管理员补齐配置，而不是回退到 `app-built-in`。
- 测试环境可使用本地文件系统 Storage Provider；宿主机挂载目录建议命名为 `./data/upload-files`，容器内路径保持 `/files`，以复用服务已有静态文件映射。
- `WecomOrganizationSyncConfig.Organization` 保存上述业务组织 `Name`。
- 企业微信原始 `CorpId` 继续保存在同步配置和映射表中，作为外部系统稳定绑定依据。

配置保存时，如果管理员仍从 `built-in` 上下文发起且提供了 Corp ID，系统应解析到 Corp ID 对应的业务组织并创建缺失组织和默认应用，返回最终目标组织给前端切换上下文。手动同步执行前也应补齐历史缺失的默认应用。前端同步目标组织选择器不展示 `built-in`，降低误选概率；手动同步执行前必须再次校验目标组织不是 `built-in`，防止绕过前端或历史配置导致权限扩大。

组织显示名更新策略：

- 首次成功同步时，从企业微信根部门快照推导显示名。
- 如果业务组织仍是自动创建的兜底显示名，允许更新为企业微信根部门名。
- 如果管理员已经手动修改过显示名，后续同步不自动覆盖，避免名称变化影响管理端识别。

### 9. 第一版不做完整 dry-run 预览

完整 dry-run 需要执行一套接近真实同步的差异计算，但又不能落库。如果同步逻辑和 dry-run 逻辑分叉，后续容易出现“预览结果”和“实际同步结果”不一致。

首版采用两个低成本控制手段：

- 配置页提供“测试连接”，校验 `corp_id`、自建应用 Secret 和通讯录读取权限。
- 每次真实同步写入执行记录，包含新增、更新、软禁用、失败数量和安全错误摘要。

后续如果业务要求上线前必须二次确认大规模变更，可以在同步服务稳定后追加 dry-run，并复用同一套同步计划计算逻辑。

## First-Version Acceptance

第一版实现应至少通过以下验收场景：

- 修改企业微信部门名称后，下一次全量差异同步更新本地 `Group.DisplayName`，但不改变 `Group.Name`。
- 移动企业微信部门后，下一次同步更新本地父子部门关系。
- 企业微信新增成员后，本地新增对应 User 和映射记录。
- 企业微信成员调整部门后，本地用户组关系只更新企业微信来源部门组，保留非企业微信来源用户组。
- 企业微信成员直属上级变化后，本地直属上级关系更新，管理范围接口返回新的直接/间接下属范围。
- 企业微信部门负责人变化后，本地部门负责人关系更新，管理范围接口返回新的部门及子部门范围。
- 企业微信同步中途失败时，同步记录为失败或部分失败，且不会软禁用未拉取到的部门和成员。
- 崩溃遗留的 `running` 同步记录过期后可恢复，不会阻塞后续手动同步。
- 普通用户没有负责人范围和直属/间接下属时，管理范围接口只返回本人范围。
- 企业微信同步配置从 `built-in` 上下文保存时，自动绑定或创建 Corp ID 对应业务组织，后续同步用户 Owner 不再是 `built-in`。
- 历史误同步到 `built-in` 的企业微信 `wecom-*` 测试数据可以按映射表和固定前缀清理，不影响 `built-in/admin` 和内置应用、权限、模型、适配器、证书。

## Migration Plan

首版采用 `aicodex-admin` 现有 Xorm 自动同步机制，而不是引入新的迁移框架：

1. 新增 7 个企业微信组织同步对象结构体。
2. 在 `object/ormer.go` 的 `createTable()` 中追加 7 个 `Engine.Sync2(new(...))`。
3. 首次部署或应用启动时，由 Xorm 创建缺失表并补齐新增字段。
4. 在测试环境 PostgreSQL 上验证表、字段、索引、`timestamptz` 时间字段、关系表查询、JSON/text 排查字段读写和唯一约束行为。

升级边界：

- 允许：新增表、新增可空字段、新增普通索引、新增状态字段。
- 谨慎：新增唯一约束，必须先确认历史数据没有重复。
- 禁止默认执行：删除字段、重命名字段、收窄字段长度、变更字段类型、批量清洗生产数据。

如果后续出现 `Sync2` 不适合承载的复杂升级，应单独补充幂等升级函数或 SQL 脚本，并满足：

- 升级脚本可重复执行。
- 执行前有表结构和数据备份。
- 每一步有可查询的验证 SQL。
- 失败时不会删除已同步的 `Group`、`User`、映射表和执行记录。

测试环境使用策略：

- 在实现阶段需要使用已部署的 `aicodex-admin` 测试环境和 PostgreSQL。
- 测试库应允许创建 7 张企业微信组织同步表。
- 如果测试库已有业务数据，验证过程只能新增企业微信同步相关表和测试数据，不能清理既有用户、组织、用户组或认证配置。
- 上线前应先在测试环境执行一次“启动建表 + 配置保存 + 连接测试 + 手动同步失败场景 + 管理范围接口空结果”冒烟验证。

## Risks / Trade-offs

- [企业微信通讯录权限不足导致只同步到部分成员] → 同步前提供配置说明，同步结果记录企业微信错误码和错误摘要。
- [同步中途失败导致误软禁用] → 只有完整全量拉取和落库成功后才允许软禁用缺失对象，失败或部分失败只记录执行结果。
- [首次同步误关联已有本地用户] → 企业微信侧以 `Corp ID + userid` 唯一识别成员；本地账号绑定只用稳定企业微信标识做主匹配。手机号、邮箱或同名只用于记录疑似本地重复账号，供管理员排查，不自动合并。
- [部门负责人字段无法表达多负责人] → 首版 `Group.Manager` 保存主负责人，完整负责人列表放入 `wecom_department_leader`，管理范围计算必须读取所有启用负责人关系。
- [把部门层级误当成上下级关系会扩大或缩小权限范围] → 直属上级只从 `direct_leader` 同步，不根据部门树、成员排序或展示层级推断。
- [Group/User 现有字段不足以表达所有企业微信信息] → 首版把部门和成员的外部标识放入映射表，把成员部门、部门负责人、直属上级放入关系表。
- [同步任务运行时间较长或进程崩溃] → 后端采用同步记录、互斥锁、心跳租约和 stale running 恢复机制。
- [下游系统使用范围接口时口径不一致] → 在接口响应中同时返回本地用户 ID、企业微信 userid 和完整 external_id，并在文档中明确推荐过滤字段。
- [企业微信普通员工误入 `built-in` 导致全局管理员权限] → 配置保存时自动绑定独立业务组织，执行同步前拒绝 `built-in`，并提供测试环境清理步骤。
