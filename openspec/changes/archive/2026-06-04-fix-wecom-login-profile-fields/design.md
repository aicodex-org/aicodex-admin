## Context

企业微信用户资料字段有两条来源：

- 登录链路：内部应用可通过 `auth/getuserinfo` 获取 `userid` 和 `user_ticket`，再通过 `auth/getuserdetail` 或通讯录 `user/get` 获取授权后的敏感字段。
- 通讯录同步链路：组织架构同步可通过通讯录接口获取 `mobile`、`email`、`biz_mail`、`avatar` 等字段，并写入本地用户。

当前问题发生在登录链路：扫码登录成功后，企业微信返回的 `mobile`、`biz_mail` 没有完整映射到 `idp.UserInfo`；同时通用 OAuth 回填逻辑只处理邮箱，不处理手机号。因此即使企业微信返回手机号，也不会补齐本地 `User.Phone`。

## Goals / Non-Goals

**Goals:**

- 企业微信内部应用登录拿到敏感字段时，能够把 `mobile` 映射为本地手机号。
- 企业微信扫码登录发起时能够携带 `snsapi_privateinfo` 等 Provider 配置的授权范围。
- 企业微信返回 `email` 为空但 `biz_mail` 有值时，能够用 `biz_mail` 作为本地邮箱兜底。
- 企业微信授权详情接口缺少敏感字段时，能够用通讯录详情接口返回的非空字段补充。
- OAuth 登录资料回填能够补齐空的手机号，并保存 Provider 侧手机号属性。
- 保持“不覆盖已有资料”的策略，避免登录流程覆盖后台手工维护或通讯录同步维护的用户资料。

**Non-Goals:**

- 不改变企业微信 Provider 的配置页面和登录入口。
- 不绕过企业微信敏感字段授权要求；如果企业微信未返回手机号或邮箱，本次变更不伪造、不推断字段。
- 不自动合并同名、同手机号或同邮箱的不同本地账号。
- 不调整企业微信通讯录同步的数据模型。

## Decisions

### 1. 在企业微信 IdP 层完成字段归一化

企业微信内部应用返回字段与本地 `idp.UserInfo` 字段不完全一致。设计上在 `WeComInternalIdProvider.GetUserInfo()` 中完成归一化：

- `mobile` → `UserInfo.Phone`
- `email` → `UserInfo.Email`
- `biz_mail` → 当 `email` 为空时作为 `UserInfo.Email` 兜底

这样控制器和 OAuth 回填逻辑不需要理解企业微信字段差异。

备选方案是在登录控制器中判断 Provider 类型并特殊处理企业微信字段。该方案会把外部 Provider 字段细节泄漏到控制器，不采用。

### 2. 企业微信扫码登录必须保留授权范围

企业微信敏感资料授权依赖登录发起 URL 中的 `scope=snsapi_privateinfo`。此前 Provider 配置中虽然可以保存 `snsapi_privateinfo`，但 `Internal + Normal` 扫码登录 URL 没有带 `scope`，首页内嵌扫码组件初始化参数也没有传 `scope`，导致企业微信侧没有机会按敏感资料授权范围处理。

修复策略：

- `Provider.getAuthUrl()` 对企业微信 `Internal + Normal` 和 `Third-party + Normal` 登录保留 Provider 配置的 `scope`。
- 首页内嵌企业微信扫码组件从登录 URL 解析 `scope`，并传给 `WwLogin` 初始化参数。
- 静默授权链路保持原有 `scope` 参数行为。

2026-06-04 测试环境验证显示，`WwLogin` 和 `login.work.weixin.qq.com/wwlogin/sso/login` 页面都会保留 `scope=snsapi_privateinfo` 参数，但 PC SSO 扫码流程仍不保证弹出敏感资料授权确认。`open.weixin.qq.com/connect/oauth2/authorize` 敏感授权入口在普通浏览器中返回“请在企业微信客户端打开链接”。因此本次修复只保证 admin 侧不会丢失 `scope`，不保证企业微信 PC 扫码一定返回手机号、邮箱或头像。

### 3. 授权详情缺字段时使用通讯录详情非空补充

企业微信登录链路可能出现 `auth/getuserinfo` 返回 `userid + user_ticket`，但 `auth/getuserdetail` 只返回 `userid`，未带手机号、邮箱、企业邮箱或头像的情况。此时在已经拿到 `userid` 的前提下，系统再调用通讯录 `user/get`：

- 若通讯录详情返回非空 `name`、`mobile`、`email`、`biz_mail` 或 `avatar`，用于补齐登录详情。
- 若通讯录详情调用失败，但授权详情已经确认了 `userid`，不阻断登录，只保持缺失字段为空。
- 合并时只补非空字段，避免空值覆盖授权详情中已拿到的字段。

该策略要求企业微信应用具备通讯录读取权限；如果企业微信侧未授权，代码不会绕过限制。

### 4. OAuth 回填只补空值，不覆盖已有本地资料

登录链路拿到的手机号、邮箱可能来自用户授权结果，也可能晚于通讯录同步。为避免登录时覆盖更可信的后台资料，回填规则保持为：

- Provider 返回字段非空时，写入 `oauth_<Provider>_<field>` 属性。
- 本地 `Email` 或 `Phone` 为空时，才补齐核心用户字段。
- 本地已有 `Email` 或 `Phone` 时保持不变。

备选方案是每次登录都覆盖本地邮箱和手机号。该方案可能覆盖管理员维护值或通讯录同步值，不采用。

### 5. 用回归测试固定字段映射和不覆盖策略

本次修复覆盖两个容易回退的点：

- 企业微信内部登录解析 `mobile`、`biz_mail`。
- 企业微信 `Internal + Normal` 登录发起 URL 和内嵌扫码组件携带 Provider `scope`。
- 企业微信授权详情缺字段时，通过通讯录详情补齐缺失资料。
- 已有用户 OAuth 登录后补齐空手机号，但不覆盖已有手机号。

测试使用本地模拟 HTTP 响应和纯对象测试，不依赖真实企业微信环境。

### 6. 运行态授权边界验证结论

真实链路验证后，本次 change 明确以下边界：

- PC 扫码 SSO 可以保留 `scope=snsapi_privateinfo`，但不保证弹出敏感资料授权确认，也不保证返回 `user_ticket`、手机号、邮箱或头像。
- 企业微信客户端内 OAuth2 敏感授权入口可以触发用户授权确认；用户同意后，`auth/getuserinfo` 可返回 `user_ticket`，`auth/getuserdetail` 可返回手机号、邮箱、企业邮箱和头像等敏感字段。
- 企业微信客户端内 OAuth2 敏感授权入口需要单独的产品入口和回调处理，本次 change 不把该入口塞入 PC 扫码登录流程。
- 通讯录详情接口只作为同源应用下的非空兜底；如果企业微信侧没有返回敏感字段，本地不会伪造或推断。

因此，本次 change 的收口目标是：保证 admin 在企业微信返回字段时能够正确落地，并保留 PC 扫码登录发起时的授权范围；敏感资料主动授权入口作为后续独立 change 处理。

## Risks / Trade-offs

- [企业微信没有返回敏感字段] → 代码无法补齐字段；需要检查企业微信应用可见范围、通讯录读取权限、敏感字段授权配置和用户授权结果。
- [PC 扫码 SSO 不触发敏感授权确认] → 前端已传入 `snsapi_privateinfo`，但真实扫码仍可能只返回基础身份；手机号、邮箱和头像需要依赖企业微信客户端内 OAuth2 授权入口，或依赖通讯录同步接口在具备权限时补齐。
- [敏感资料授权入口未接入] → 当前登录流程只能消费企业微信已返回的字段；用户主动补齐手机号、邮箱和头像需要后续 change 增加企业微信客户端内授权入口。
- [已有用户资料错误但非空] → 登录回填不会覆盖；需要管理员手工修正或通过后续通讯录同步策略处理。
- [第三方服务商登录字段口径不同] → 本次只修内部应用登录链路；第三方服务商链路保持现状，后续单独验证。

## Migration Plan

1. 部署修复后，无需新增数据库表或执行迁移。
2. 已经登录过但邮箱/手机号为空的用户，需要重新通过企业微信登录，或等待下一次企业微信通讯录同步补齐。
3. 若部署后发现回填行为异常，可回滚本次代码；已补齐的本地字段不会被回滚自动清空。
