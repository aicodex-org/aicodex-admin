## Context

当前企业微信同步页已经具备配置保存、连接测试、启动全量同步和同步记录列表展示能力。后端列表接口 `/api/wecom-org-sync/runs` 已返回运行状态、阶段、执行人、开始/结束时间，以及部门/用户的新增、更新、禁用统计；单条详情接口 `/api/wecom-org-sync/runs/:runId` 也已存在。前端问题主要集中在两个方面：

- 同步记录里的统计值被压缩成 `a/b/c` 裸数字，管理员需要依赖表格外的“新增 / 更新 / 禁用”提示才能理解含义。
- 手动启动同步后页面只刷新一次，后续运行中状态不会继续更新，管理员只能整页刷新才能观察进度。

这次 change 聚焦于 `web-admin` 页面交互，不调整同步算法、运行状态模型、后端 API 契约或数据库结构。

## Goals / Non-Goals

**Goals:**

- 让同步记录里的“部门 / 用户”统计在表头或单元格内即可自解释。
- 在存在 `running` 记录时自动刷新同步记录，直到全部进入终态。
- 提供手动刷新入口，作为管理员主动确认和自动轮询失败时的兜底。
- 让同步记录表格分页可正常切换历史页，避免出现“看得到页码但点不动”的伪分页。
- 当页面已识别到运行中任务时，避免继续把“开始全量同步”作为可执行动作暴露给管理员。
- 避免页面在账号或配置尚未就绪时出现空白首屏。
- 让管理员可见当前是否处于自动刷新观察中，以及最近一次同步记录刷新时间。
- 保证轮询在切换组织、页面卸载、全部终态或请求失败时被正确清理，避免重复请求和提示噪声。
- 统一 admin 端列表页的分页默认配置，减少相同分页参数在各页面重复散落。

**Non-Goals:**

- 不新增 WebSocket、SSE 或新的后端推送机制。
- 不变更现有 `/api/wecom-org-sync/runs`、`/api/wecom-org-sync/runs/:runId` 返回结构。
- 不调整同步阶段划分、统计口径或失败分类逻辑。
- 不在本次 change 中扩展同步详情抽屉、历史筛选器或多页联动观察面板。
- 不处理 `ManagementPage`、`Form.Item` 等与本页运行监控无直接关系的全局 warning。

## Decisions

### 1. 采用“列表轮询”为主，而不是新增推送机制或强依赖单条详情轮询

采用现有 `GET /api/wecom-org-sync/runs` 作为自动刷新主数据源，继续请求当前组织第一页同步记录列表。

选择原因：

- 当前列表接口已经返回前端展示所需的状态、阶段和部门/用户统计，不需要新增后端字段。
- 现有列表默认按 `createdAt` 倒序返回，最新 run 位于第一页，能够覆盖管理员启动同步后的主观察路径。
- 相比 WebSocket/SSE，列表轮询不引入新的连接管理、后端推送语义和部署复杂度，更符合这次小范围体验增强。

备选方案：

- 单条 run 详情轮询：可用，但当前页面主要观察的是列表区域，仍需要同步更新列表，不如直接轮询列表统一。
- WebSocket/SSE：实时性更强，但对本次问题属于过度设计。

### 2. 采用“自动轮询 + 手动刷新”双机制

页面在发现当前列表存在 `running` 记录时，启动固定间隔自动刷新；同时在同步记录区域提供显式“刷新”按钮。

选择原因：

- 自动轮询解决“启动后页面不再变化”的主问题，符合后台长任务观察的标准体验。
- 手动刷新提供明确控制权，可用于管理员刚切组织、刚保存配置、轮询失败后复核，避免只能整页 F5。
- 两者组合比“只加按钮”更完整，也比“只自动轮询”更稳妥。

实现约束：

- 轮询间隔固定为 3 秒，优先保证观察及时性，同时控制请求频率。
- 若一次自动刷新失败，停止自动轮询并保留手动刷新，避免持续报错刷屏。

### 2.1 运行中时收紧启动入口，并把竞态冲突视为提示而不是失败

当页面已通过列表识别到当前组织存在 `running` 记录时，`开始全量同步` 按钮切为禁用态，并用更直接的按钮文案表达“同步进行中”。

选择原因：

- 页面已经知道当前存在运行中任务时，再保留可点击启动入口，只会制造“点击后被后端拒绝”的体验噪声。
- 后端“拒绝重复启动”仍然保留，前端禁用只是把大多数正常场景前置拦住，减少无意义请求和误导性失败提示。

竞态兜底：

- 即使页面已禁用按钮，仍可能存在多标签页、多个管理员并发、页面状态短暂滞后的情况。
- 当后端返回 `wecom organization sync run is already running` 时，前端不再提示“同步失败”，而是提示“已有同步任务在运行，已刷新同步记录”，并立即刷新列表，回到当前真实运行态。

### 2.2 同步记录历史页采用标准表格分页，第一页仍作为最新运行态观察面

同步记录列表继续使用现有 `/api/wecom-org-sync/runs` 分页参数，但前端需要把 `current/pageSize/total` 纳入受控状态，点击分页后重新请求对应页数据。

选择原因：

- 当前后端列表接口已经支持 `p` 和 `pageSize`，前端不需要新增接口即可修复“分页导航失效”问题。
- 同步任务的最新记录天然位于第一页；把第一页继续定义为“最新运行态观察面”，可以兼顾实时观察和历史浏览。

实现约束：

- 管理员切换到第 2 页及以后时，页面展示历史记录视图，不再把当前页误导为最新运行状态观察面。
- 管理员从历史页触发新的全量同步，或命中 `already running` 兜底提示时，页面刷新后返回第一页，以便直接看到最新运行记录。

### 2.3 共享分页能力用 helper 收口，而不是自定义一套视觉分页组件

admin 端大部分列表页已经依赖 Ant Design `Table` 的内置分页；本次不额外包一层新的分页 UI，而是提取共享 helper，统一：

- 默认 `current/pageSize`
- `showQuickJumper`
- `showSizeChanger`
- 总数文案 `showTotal`

选择原因：

- 当前重复主要是分页配置对象，不是分页 DOM 结构；抽 helper 比重包分页组件更贴合现有架构。
- BaseListPage 派生页和少量独立列表页都可以复用同一 helper，收益明显且改动风险可控。

### 3. 统计语义直接绑定到表格结构，不保留悬空提示

同步记录区域不再依赖表格外单独放置“新增 / 更新 / 禁用”静态说明。语义直接体现在：

- 列头：例如 `部门（新增 / 更新 / 禁用）`、`用户（新增 / 更新 / 禁用）`
- 或单元格：例如 `新 0 / 更 254 / 禁 0`

选择原因：

- 数据和语义应在同一视觉对象内闭环，降低管理员来回对照成本。
- 这比仅仅“把提示挪近一些”更符合自解释表格的后台设计标准。

### 4. 轮询生命周期跟随当前组织和页面实例

轮询定时器由 `WecomOrganizationSyncPage` 自身持有，并严格绑定当前组织上下文。

规则：

- 页面首次加载或切换组织后，先拉一次列表，再根据是否存在 `running` 记录决定是否启动轮询。
- 切换组织时，先清理旧组织的轮询，再进入新组织刷新逻辑。
- 页面卸载时清理轮询，避免后台定时器继续运行。
- 当列表中的所有记录都进入终态时，自动停止轮询。

这样可以避免多定时器并发、旧组织数据覆盖新组织页面，或组件卸载后继续 `setState`。

### 5. 刷新反馈在页内闭环，而不是只依赖 toast

同步记录区域增加一行轻量状态文案，用于说明：

- 当前是否检测到 `running` 记录并持续自动刷新
- 当前无运行中任务时可以手动刷新
- 最近一次成功刷新时间
- 自动刷新失败后已暂停，需要手动重试

选择原因：

- toast 只适合瞬时事件，不适合表达“页面正在持续观察什么”。
- 管理员在长任务观察时需要稳定的、可回看的页内状态，而不是依赖记忆刚才有没有提示。
- 这类文案完全基于前端已有状态推导，不需要新增后端字段。

### 6. 首屏至少展示页级加载态

当账号组织尚未注入、或同步配置仍在首次拉取时，页面继续展示标题和简短加载说明，不再返回空白 DOM。

选择原因：

- 空白首屏会让管理员误判为页面异常、权限问题或路由未命中。
- 这次 change 既然聚焦“运行监控体验”，就应顺手补齐最基础的感知反馈。

## Risks / Trade-offs

- [列表只轮询第一页，未来若运行中记录不在第一页可能漏看] → 当前默认按 `createdAt` 倒序展示，管理员刚触发的 run 会位于第一页；若后续页面支持自定义排序或分页观察，再补充更细粒度策略。
- [管理员停留在历史页时，页面不再自动代表最新运行态] → 明确用页内提示说明“返回第 1 页可观察最新运行状态”，并在管理员触发新同步后主动回到第一页。
- [自动轮询失败时用户误以为状态仍在更新] → 自动轮询失败后立即停止，并保留手动刷新入口与错误提示。
- [过于频繁的自动刷新增加后台请求] → 采用 3 秒固定间隔，且仅在检测到 `running` 记录时轮询；全部终态后立即停止。
- [表头信息过长影响表格紧凑度] → 优先在列头补足语义，必要时用紧凑文案或在单元格中用短标签表达，不恢复表格外悬浮说明。
- [前端禁用按钮后仍可能遇到后端重复运行冲突] → 视为并发兜底场景，前端改为提示并刷新，而不是继续展示为失败。

## Migration Plan

该 change 只涉及前端页面、测试和 OpenSpec 文档，不涉及数据库迁移或后端接口升级。

实施顺序：

1. 更新 `WecomOrganizationSyncPage` 的同步记录展示、受控分页与轮询逻辑。
2. 提取共享分页 helper，并接入 BaseListPage 体系与独立列表页中的通用分页配置。
3. 补充 `WecomOrganizationSyncPage.test.js` 与 helper 测试，覆盖统计展示、自动轮询、手动刷新和历史页翻页。
4. 运行前端相关测试、构建与 OpenSpec 校验。

回滚方式：

- 如需回滚，只需恢复前端页面与测试改动，不影响已有同步数据和 API。
