## Context

企业微信和飞书同步页面近期已经迁移到共享的 provider 品牌页头和操作栏。运行态截图显示仍有不一致：飞书把 dry-run、身份匹配和交接资料放在与基础同步流程近似的视觉层级，正式同步记录表也曾把多个概念压在少数列里；企业微信则更清爽，操作路径更直接。

## Goals / Non-Goals

**Goals:**

- 让企业微信和飞书首屏流程一致：配置来源、测试连接、飞书可选预览、启动同步、查看正式同步记录。
- 保留飞书专有能力，但除非存在错误、警告或管理员主动展开，否则默认作为次级状态和入口。
- 统一正式同步记录表的基础语义，降低管理员在两个 provider 页面之间切换的学习成本。
- 保持实现小而前端-only。

**Non-Goals:**

- 本 change 不把飞书 dry-run、交接资料或身份匹配诊断补到企业微信；后续确认收益后可单独补齐。
- 不改变同步执行、诊断计算、脱敏/导出 payload 或后端 API 契约。
- 不在本次 polish 中把整个飞书页面从 JS 迁移到 TSX。
- 不重做认证中心整体 shell。

## Decisions

1. **以企业微信作为基础同步流程参考。**  
   企业微信页面已发布且更清爽。飞书保留额外能力，但基础配置、主操作和正式记录应遵循同一操作心智。

2. **使用已有共享外壳，避免大范围组件重写。**  
   在已有组织同步前端 shell 上做小范围展示调整。provider 页面自己的状态和后端调用继续留在原文件中，降低行为回归风险。

3. **把飞书辅助能力视为次级检查和交接资料。**  
   身份匹配和交接资料默认是一行状态摘要，保留刷新、详情、复制和导出入口。dry-run 历史放在预览操作附近，用弹窗查看，不在主页面默认展示完整表格。

4. **正式同步记录保持显式列。**  
   使用运行 ID、状态、触发方式、阶段、执行人、开始时间、结束时间、部门影响、用户影响、飞书成员关系影响和安全错误摘要。成功记录不默认显示厚重诊断块，失败或部分成功才显示紧凑诊断信息。

## Risks / Trade-offs

- **风险：飞书专有诊断不如以前显眼。** 缓解：保留明确详情按钮；只有警告、阻断或错误时才提升为告警。
- **风险：表格列增加。** 缓解：长 ID 和摘要使用截断，常见桌面宽度下避免强制横向滚动，只保留对正式记录扫描有帮助的 provider 专有列。
- **风险：飞书页面仍是较大的 legacy JS 文件。** 缓解：本次只做局部展示调整，不混入完整 TSX 迁移。
