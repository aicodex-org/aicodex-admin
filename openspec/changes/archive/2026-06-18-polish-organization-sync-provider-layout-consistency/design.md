## Context

企业微信和飞书组织同步页面已经使用相近的 Admin 同步流程，但配置区的字段排布和同步记录表头仍有差异。企业微信当前把 `corpId` 与 `addressBookSecret` 展示为企业微信专有标签，字段行节奏也不同；飞书正式同步记录表头使用较长的“新增 / 更新 / 禁用”说明，在当前列宽下会换行，影响扫描体验。

本次调整只处理 Web Admin 展示层，让两个 provider 的基础同步流程更像同一类能力。飞书 dry-run、身份匹配、交接资料和验收资料仍作为飞书专有辅助能力保留，但不在本次 change 中继续扩展。

## Goals / Non-Goals

**Goals:**

- 让企业微信配置区采用与飞书一致的三行节奏：目标组织、凭据、同步选项/定时同步。
- 将企业微信凭据展示标签统一为 `App ID（Corp ID）` 和 `App Secret`，但保持现有后端字段和接口契约不变。
- 将企业微信和飞书正式同步记录统计列表头短化，避免飞书列头换行；统计含义继续由单元格中的 `新 / 更 / 禁` 表达。
- 保持现有页面加载、错误、保存、测试连接、手动同步和记录刷新行为。

**Non-Goals:**

- 不新增企业微信 dry-run、身份匹配、交接资料或验收资料。
- 不删除或弱化飞书已有 dry-run、身份匹配、交接资料能力。
- 不修改后端 API、数据库、同步执行、调度、OAuth/OIDC、Gateway 或 Insight。
- 不读取真实 provider secret，不触发真实租户同步。

## Decisions

1. 企业微信配置区只调整 Row/Col 排布和标签文案。

   原因：本次目标是 provider 布局一致性，`corpId` 和 `addressBookSecret` 的后端语义已经稳定。直接改展示标签能降低管理员切换 provider 时的认知成本，同时避免接口和数据迁移风险。

2. 企业微信第一行右侧保留桌面占位，不新增“服务区域”假字段。

   原因：企业微信没有飞书的 endpoint mode 概念。用桌面占位保持两列栅格对齐，比新增无意义字段更符合 KISS；移动端不应额外渲染明显空白。

3. 正式同步记录统计列表头使用短标签。

   原因：表头长文案在飞书页面会换行，导致表格视觉拥挤。统计单元格已经用 `新 / 更 / 禁` 明确表达含义，短表头足以让管理员扫描差异，同时让企业微信和飞书的同步记录更一致。

4. 测试聚焦可见标签和已有页面行为。

   原因：本次没有新增业务逻辑。测试应覆盖标签、列头和页面基础渲染，不引入低价值 mock 细节。

## Risks / Trade-offs

- 短表头减少了列头自解释程度 → 通过保留单元格 `新 / 更 / 禁` 格式和既有统计顺序降低误解风险。
- 企业微信右侧桌面占位可能在小屏形成空白 → 实现时仅在中等及以上布局保留占位，小屏按自然单列流式展示。
- 飞书仍比企业微信多辅助能力 → 本次只降低基础区和记录区差异，不把飞书专有能力删除或强行移植到企业微信。
