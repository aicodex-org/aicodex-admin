## Context

当前同步记录表更偏日志表：首列直接展示 `runId`，排障时有用，但管理员日常查看更多关注状态、触发方式、时间和影响数量。截图中企业微信和飞书两边也还有细节差异：飞书定时同步输入没有小标签，执行人列在企业微信容易换行，飞书 `错误摘要` 表头在当前列宽下会换行。

本次是展示层小收口，目标是让两个同步页继续保持“主流程一致、provider 专有能力轻量存在”的方向。

## Goals / Non-Goals

**Goals:**

- 正式同步记录默认展示分页连续序号，而不是占宽的完整 `runId`。
- 保留完整 `runId` 的排障能力，不改变 `rowKey` 或后端定位字段。
- 两个 provider 的执行人列长文本都采用省略展示，并可通过 tooltip 查看完整值。
- 飞书定时同步输入补齐 `Cron 表达式`、`时区`标签。
- 飞书 `错误摘要` 表头保持单行，不再出现列头换行。
- 统计数量使用稳定数字宽度样式，减少数字列视觉抖动。

**Non-Goals:**

- 不新增、删除或重排飞书 dry-run、身份匹配、交接资料能力。
- 不修改后端 API、同步 run 数据结构或分页协议。
- 不把企业微信补齐为飞书同等辅助诊断能力。
- 不进行全页 TS 迁移或组件大重构。

## Decisions

1. 表格首列使用分页序号，`runId` 放到 tooltip 和复制文本中。

   原因：序号更适合后台列表扫读；完整 ID 只在排障时需要。保留 `rowKey="name"`，不影响表格稳定性和后端定位。

2. 序号按分页计算。

   原因：第 2 页从 11 开始能体现全局位置，避免每页都从 1 开始造成历史记录定位歧义。

3. 执行人列用 `Typography.Text` 省略和 `Tooltip`。

   原因：执行人可能是 `scheduler:<hash>` 或 `built-in/aicodex-admin`，直接换行会拉高行高；tooltip 能保留完整信息。

4. 飞书定时同步沿用企业微信的小标签布局。

   原因：这是已确认的统一配置节奏，不需要抽新组件就能解决可读性差异。

5. 表头不换行用局部列头样式解决。

   原因：这属于表格密度问题，不需要改变后端字段或合并列。对 `错误摘要` 等短表头添加 `whiteSpace: nowrap` 能保持列头稳定。

## Risks / Trade-offs

- 序号默认隐藏完整 `runId` → 通过 tooltip 和 copyable 保留排障入口。
- `Tooltip` 增加 hover 交互 → 只用于长 ID/执行人，主表仍可直接扫读。
- 飞书页面仍是 legacy JS → 本次只做局部兼容修改，不在小 polish 中迁移整页。
