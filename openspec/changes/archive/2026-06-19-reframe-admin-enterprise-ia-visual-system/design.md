## Context

本路线已经合入多轮企业认证中心改造，包括视觉语言、组织身份工作台、接入预检、治理任务队列、对象证据链和关系聚合前端 fallback。它们提升了能力覆盖，但也暴露新的产品风险：抽象治理入口过多时，Admin 会变忙，却不一定更容易完成认证中心的核心运维判断。

本 change 原本同时覆盖 IA、视觉系统、对象上下文和验证门禁。归档前收口时只保留已经完成并合入的 IA audit/navigation reframe 与后续任务门禁；未完成的视觉系统实现、对象上下文迁移和浏览器/60 证据不再留在本 umbrella 的 active checklist 中，统一作为未来独立 change 的候选。

修正后的产品方向合并两条领导反馈：

- Admin 在部分页面仍偏普通 CRUD 后台，需要更成熟的企业控制台气质。
- 这种成熟度不应通过继续增加治理中心、入口卡片或解释面板实现。

下一阶段若继续做 UI，应通过业务域信息架构、密度、表格工具面、对象详情、证据和一致语言提升专业度，而不是新增显眼入口。

## Goals / Non-Goals

**Goals:**

- 把主导航重新框定为业务域，而不是实现模块或抽象治理能力。
- 明确关系、证据、预检、治理任务和快捷操作的默认放置位置。
- 给未来 UI worker 一个可验证的拒绝/接受规则，避免继续新增 filler 入口。
- 保留当前 React + TypeScript 迁移规则和验证期望作为后续独立 change 的门禁。

**Non-Goals:**

- 本次归档不实现新的 UI、导航、样式、对象抽屉或浏览器验证证据。
- 本次归档不删除已有已实现能力，也不移除既有路由。
- 本次归档不改写 `propose-admin-enterprise-identity-governance-experience-layer` 的已合入事实；该 umbrella 由本轮另行收口。
- 本次归档不新增后端写行为、真实认证执行、Gateway 执行行为、生产/测试分支变更。

## Decisions

### Decision 1: 主 IA 以业务域为中心

主导航应围绕稳定业务域组织：中心总览、组织与账号、应用接入、身份源、权限与角色、审计运维和 LLM AI/Gateway。抽象治理能力不应作为第一层概念与这些业务域竞争。

替代方案是继续把每个新增能力都作为菜单项。该方案会让导航分类反映实现历史，而不是管理员意图。

菜单标签和菜单文档命名也应服务扫描效率：一级菜单默认四字中文业务名优先，不使用过长解释性短语；LLM AI/Gateway、OAuth/OIDC、Provider、MCP 等专有技术词允许中英混合。该规则只作为 IA/文案门禁，不要求本次归档修改 `web-admin/src/**`、locale 或实现代码。

### Decision 2: 横向治理能力默认上下文化

关系、证据、预检、治理任务和快捷操作仍然有价值，但默认位置应调整为：

- 关系和证据进入对象详情、抽屉、行操作或对象页。
- 预检进入创建/配置流程和结果页。
- 治理任务在没有后端聚合和处理闭环前，只作为总览待处理提示或对象风险提示。
- 快捷操作保留在总览或对象操作区，不扩展成独立快捷操作中心。

替代方案是保留所有横向能力的独立中心。该方案要求管理员先学习产品内部抽象，再回答业务问题。

### Decision 3: 视觉系统和对象上下文实现拆出

紧凑页头、专业表格工具栏、对象详情迁移、状态语言和浏览器证据仍是正确方向，但本 umbrella 没有完成对应实现和验证。它们不能以未完成 checklist 继续留在 active change 中，也不能在归档时伪装成已经交付。

后续如继续推进，应拆成独立小 change，并在 proposal/tasks 中说明目标页面、写集、验证层级和浏览器证据。

### Decision 4: 后续 UI 任务必须绑定管理员决策

只新增菜单、中心、卡片、状态条或说明区不构成合格任务。后续工作必须说明它如何帮助管理员判断：谁能登录、通过哪个身份源、哪些应用可访问、风险在哪里、证据在哪里、下一步应修什么。

替代方案是接受独立小 UI polish。该方案会增加路线噪声，并让产品方向难以跨 worker 恢复。

## Deferred Work

以下工作从本 umbrella scope 中裁出，不在本次 archive 中声明为已完成：

- `DEFER`: 紧凑企业页头、表格工具栏、状态标签和页面密度实现。
- `DEFER`: 代表性页面的大工作台/卡片堆叠替换。
- `DEFER`: 空态、加载态、错误态、权限态和 cannot-infer 状态的视觉系统统一。
- `DEFER`: 将关系、证据、预检、治理任务和快捷操作迁移到对象详情、行操作或流程内。
- `DEFER`: Playwright/local-dev/60 桌面和移动端截图证据、表格首屏坐标和 console 证据。

## Risks / Trade-offs

- [Risk] `/identity-assets`、`/access-wizard`、`/governance-tasks` 等已实现路由可能仍作为独立入口存在。Mitigation: 本 change 不要求立即删除；后续实现应在保留深链和兼容 redirect 的前提下降级或上下文化。
- [Risk] 降低显眼入口可能隐藏有用能力。Mitigation: 通过总览提示、对象级动作和流程内入口，在相关时刻保持可发现。
- [Risk] 视觉系统 polish 可能变成大重构。Mitigation: 后续独立 change 应按导航 map、shell/page header、table toolbar/status language、object detail pattern 拆小推进。
- [Risk] 浏览器证据成本较高。Mitigation: 后续实现只要求代表性路由的截图和 DOM 检查，不要求一次性覆盖所有页面。

## Migration Plan

1. 本次 archive 只同步 IA 降级和后续 UI 任务门禁到主规格。
2. 未来如需要视觉系统实现，单独开 change 选择代表性页面，明确桌面/移动验证路径。
3. 未来如需要对象上下文迁移，单独开 change 处理对象详情、行操作或流程内入口，并保留现有深链。
4. 每个后续 change 都必须说明它改善的管理员决策和核心操作位置，不得只新增入口或说明卡片。

Rollback 策略：既有路由和稳定 key 保持兼容；如果导航降级导致发现性问题，可以恢复入口，同时保留业务域分组和对象上下文动作。

## Open Questions

- `/identity-assets`、`/access-wizard` 和 `/governance-tasks` 应作为二级叶子、隐藏于主导航，还是只从总览/对象上下文暴露，需要未来独立实现 change 结合截图评审决定。
- 是否需要单独的 `web-admin` 设计 token 或组件指南，应在第一个视觉系统实现 slice 形成可复用模式后再判断。
