## Context

企业微信同步和飞书/Lark 同步都以 Admin 业务组织为目标写入本地身份资产。配置、mapping 和 run 表按 Provider 分离，但 `User`、`Group`、用户组成员关系、禁用状态和平台主数据投影是共享资产。同一个业务组织同时配置两套通讯录主数据源时，后续启用或同步可能覆盖共享用户字段、禁用状态或登录绑定判断。

两个同步页当前在全局 Admin 视角下默认使用当前账号/request organization。实际同步组织经常是保存配置后由企业微信 Corp ID 或飞书 tenant_key 派生出来的业务组织，导致管理员进入页面后需要重新选择组织才看到真实配置和记录。

## Goals / Non-Goals

**Goals:**

- 页面进入时自动定位到该 Provider 已配置或最近选择的同步目标组织。
- 同一个业务组织最多允许一个通讯录同步 Provider 处于已配置/占用状态。
- 后端在保存启用配置、手动启动同步和定时同步派发前兜底校验互斥规则。
- 同组织已有另一 Provider 配置时，当前 Provider 配置只读展示，不允许保存草稿、启用或正式同步。
- 组织选择下拉过滤已被其他通讯录来源占用的组织，避免管理员误选已归属其他来源的业务组织。

**Non-Goals:**

- 不迁移或自动合并既有企微/飞书用户。
- 不删除历史配置、mapping、run 或同步记录。
- 不改变 OIDC 登录绑定规则。
- 不引入新的外部依赖或后台异步迁移。

## Decisions

1. **互斥规则落在后端服务层，前端只做体验提示。**

   保存 `isEnabled=true`、启动同步和调度派发都可能绕过页面，因此后端必须是事实边界。前端展示冲突只是让管理员在保存前理解原因。

2. **同组织已有另一来源配置时不再保存未启用草稿。**

   用户验证发现“保存成功”会被理解为该组织可以继续配置第二套通讯录同步。为保持数据面干净并降低误操作，同组织已有另一 Provider 配置时，当前 Provider 页面只读展示配置和记录；保存、启用和正式同步都被拒绝。如需验证其他通讯录来源，应新建组织后配置，暂不提供解除或切换入口。

3. **默认组织恢复使用后端建议 + 本地最近选择。**

   后端暴露 Provider 的已配置组织和冲突状态，用于跨浏览器/跨管理员稳定恢复；前端记录最近手动选择，用于多配置场景下保持操作者上下文。若本地组织不可用或无权限，前端回退到后端建议组织。

4. **冲突状态复用配置响应而非新增复杂工作台。**

   当前问题发生在企微/飞书同步页，最小改动是在配置响应中返回 `defaultOrganization`、`isConfigured`、`conflictingProvider`、`conflictingOrganization`、`conflictingConfigured`、`conflictingEnabled`、`conflictingOrganizations` 等摘要，页面据此提示、过滤已占用组织并禁用操作。

## Risks / Trade-offs

- **已有线上组织同时配置两套来源** → 新规则会阻止后续保存配置或启动同步；页面应显示明确冲突并引导管理员新建组织验证其他来源。
- **多个业务组织都配置了同一 Provider** → 后端只能给出稳定建议组织；前端本地最近选择决定默认进入哪个组织，选择框仍保留。
- **只做前端禁用不够** → 后端保存、手动运行和调度入口都要校验，避免 API 调用绕过。
- **查询默认组织需要扫描配置表** → 配置表规模远小于用户/关系表，按 `updated_at` 或 `created_at` 取最近配置即可，避免新建索引和迁移。
