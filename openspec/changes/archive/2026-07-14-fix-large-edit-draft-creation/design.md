## Context

统一大型编辑壳迁移只改造了页面结构，保留了旧列表页“先创建空记录、再进入编辑页”的流程。因此新增对象已在后台持久化，编辑页只能靠取消或返回时调用删除接口补偿。邀请码和同步器已验证更安全的路由草稿模式，本 change 将其推广到其余七个统一编辑壳对象。

## Goals / Non-Goals

**Goals:**

- 让应用、组织、用户、群组、角色、权限和 Provider 的新增对象只在明确保存时写入。
- 保持既有默认值、校验、编辑更新、返回 URL、消息、路由路径和 payload 字段兼容。
- 对应用“复制”采用同一草稿语义，避免取消复制时留下已创建副本。
- 以自动化测试和全非 GET 拦截的受控浏览器 smoke 证明新增草稿不产生写入。

**Non-Goals:**

- 不改变后端新增、更新、删除接口，不迁移真实数据，不修改权限或外部同步逻辑。
- 不将同一规则扩展到未迁移为 `LargeEditShell` 的历史编辑页。
- 不改变已正确实现草稿语义的邀请码和 Syncer 页面。

## Decisions

### 1. 路由 state 承载新增草稿

列表页继续用既有 `new*()` 默认值生成对象，但仅通过 `history.push({ pathname, state: { mode: "add", <object> } })` 传递草稿。编辑页新增模式优先读取该对象，且跳过详情 GET。相比在 URL 中序列化对象或引入全局 store，这保留现有路由且不泄漏敏感配置字段。

### 2. 编辑页按模式选择新增或更新

保存前继续执行原有页面校验。`mode === "add"` 时调用该对象已有的 `add*` API；编辑模式继续调用 `update*`。创建成功后更新路由参数和状态为编辑模式，防止二次保存再次新增。失败时保留草稿和提交状态恢复语义。

### 3. 放弃草稿只做前端导航

新增模式的取消、返回和脏数据确认回调直接返回各自列表/既有 return URL，不调用 `delete*`。编辑模式现有取消、返回与真实删除行操作保持不变。该规则避免“放弃编辑”本身形成新的写入。

### 4. 在页面级测试覆盖读写边界

先为每个列表页加入“添加/复制不调用新增 API”的 RED 测试；再为编辑页加入草稿加载、保存新增、保存后更新、取消/返回不调用 mutation 的 RED 测试。仅 mock 必要 backend 边界，断言用户可观察的导航、提示与实际 mutation 选择。

### 5. 替代入口复用同一路由草稿契约

群组树的根/子群组入口，以及企微、飞书、钉钉组织同步页的目标组织入口直接传递完整路由草稿，不在公共 helper 或树节点 handler 中预调用新增 API。组织同步 helper 缺少可传递 route state 的 history 时 fail-closed，不回退到会丢失草稿的 URL 导航。

### 6. 用户组织上下文按最后一次选择原子生效

用户新增或编辑页的组织详情、应用、群组和编辑模式用户应用属于同一组织上下文。初始加载和组织切换均先进入 loading，仅当全部关键读取成功且 requestId、当前 owner 仍匹配时进入 ready；业务错误、缺失数据、网络异常和卸载后的晚响应均不得放行保存或覆盖新上下文。

### 7. 新增后回读持久化对象再允许更新

应用和用户的新增接口会补齐或归一化服务端字段。点击“保存”并停留时，页面先转为编辑路由，但保存类操作保持 fail-closed：应用必须成功回读持久化应用；用户必须同时成功回读持久化用户及其组织应用上下文，之后才能执行首次更新。回读失败时保留取消和返回恢复路径，卸载后的晚响应不得更新页面或显示全局错误。点击“保存并返回”时页面直接离开，不执行无意义的编辑态回读。

## Risks / Trade-offs

- [直接打开新增 URL 且缺少路由草稿] → 维持现有 404/空数据保护；正常入口始终传递草稿。
- [对象页面依赖多项并行只读加载] → 仅跳过不存在对象的详情 GET，组织、下拉、应用和辅助数据仍按既有读取路径加载。
- [应用复制曾立即写入] → 改为预填草稿后才创建，取消复制不再产生副本；这是与新增一致且用户可预期的行为修复。
- [浏览器接入 60 后台] → 只使用本地前端代理做页面观察，并在 Playwright route 层拒绝所有非 GET，避免真实写入。
- [替代入口遗漏] → 在群组树和三个组织同步页的实际按钮测试中显式断言 add/update/delete 零调用，并纳入受控浏览器 smoke。
- [用户快速切换组织] → 以 requestId + owner 双重校验丢弃旧响应，加载/错误期间保存双重 fail-closed，卸载时主动使请求失效。
- [新增成功后以前端草稿继续更新] → 应用和用户均先回读持久化对象；用户还需重建组织应用上下文，避免覆盖服务端生成或归一化字段。
- [回读失败但对象已创建] → 禁止继续保存，保留取消和返回，由管理员从列表重新进入持久化对象。
