## Context

Admin 企业认证中心路线已经把多个列表页升级为企业身份相关控制台：总览、组织身份、认证源、应用接入、审计运维和 LLM AI/Gateway 均有只读状态摘要、入口聚合和风险提示。但这些能力仍主要以“当前页面上方的状态层”为单位，管理员要判断一个用户、应用、认证源或 Gateway 映射的完整影响时，需要在组织、用户、角色、权限、应用、认证源、审计记录和 LLM AI/Gateway 页面之间手工跳转。

当前并行实现 worker 正在修正非组织身份页面的视觉语言、首屏密度、旧 Tour 和 i18n 文案。本 proposal 不与其共享写集，不要求同时调整现有页面样式细节，而是定义下一阶段可实施的信息架构和产品流程。

关键约束：

- P0 必须能在后续 1-2 个小 change 内落地，不依赖真实认证链路、OAuth/OIDC 回调执行或 Gateway projection publish 改造。
- P0 可以使用当前前端列表、分页 total、已加载行、既有路由和既有只读状态，但必须标记为当前视图或当前筛选口径。
- 需要跨列表、跨组织或全量事实时，必须定义为后续只读聚合接口或后端事实源，不得由前端当前列表推导后伪装成全局事实。
- 后续新增 React 体验组件默认 `.tsx`，新增类型、模型、数据转换和接口模型默认 `.ts`。

## Goals / Non-Goals

**Goals:**

- 定义身份资产关系层，使管理员能从对象进入详情、关系、时间线和审计证据链。
- 定义治理任务中心，使管理员能扫描、筛选、解释和处理跨域身份治理待办。
- 定义接入体验层，使认证源、应用接入和 Gateway/LLM AI 映射具备向导化配置、预检、测试连接、启用前检查和结果页。
- 形成 P0/P1/P2 阶段拆分，让后续 implementation worker 可以小步实施和验证。
- 明确每个能力的用户、入口、核心对象、页面/组件边界、数据来源、失败/空态和验证方式。

**Non-Goals:**

- 不实现 UI 代码，不修改现有页面、Tour、App.less、locale、测试、package 或 lockfile。
- 不改变真实认证、授权、OAuth/OIDC 回调、Provider 登录匹配、Gateway projection publish/cleanup/receipt、生产/类生产配置或破坏性数据。
- 不把本 proposal 产物 archive，不合入或 push `hfl-test-base` / `test`。
- 不定义写入型治理任务持久化、审批流、真实自动修复或跨服务数据同步执行。

## Decisions

### Decision 1: 先定义三条横向体验能力，而不是继续扩展单个列表工作台

选择：新增 `asset relationship layer`、`governance task center` 和 `connection wizards` 三个 capability。

理由：现有规格已经覆盖各页面的只读工作台语义，继续在每个页面上加卡片会重复同质化问题。横向体验层把“对象关系、待办治理、接入流程”作为下一阶段的产品骨架，可以复用现有页面，又能推动 Admin 更像企业级认证中心。

替代方案：修改现有认证源、应用接入、审计运维和 LLM AI/Gateway specs。该方案会把下一阶段体验散落到多个 spec，容易与正在进行的视觉语言实现 worker 冲突，也不利于后续按 P0/P1/P2 拆分。

### Decision 2: P0 只做前端只读关系和任务候选，P1 才引入全局聚合接口

选择：P0 使用当前页面列表行、分页 total、已加载行、既有详情接口和既有路由生成对象详情、关系提示和治理候选；P1 定义只读聚合接口提供跨域关系、证据链、任务汇总和预检结果；P2 再考虑治理状态历史和更完整流程。

理由：P0 可以快速交付产品体验，不需要真实认证链路或后端事实源重构。只读聚合接口涉及跨域事实归属、权限过滤、脱敏和性能，需要单独 change 明确契约。

替代方案：P0 直接新增后端全量治理聚合接口。该方案对数据口径、安全脱敏和后端查询成本要求更高，超出 1-2 个小 change 的可控范围。

### Decision 3: 对象详情优先用抽屉或轻量详情页，不替代现有列表主任务

选择：资产关系层 P0 在组织、用户、角色、权限、应用、认证源、LLM AI/Gateway 和审计记录页面提供对象详情抽屉或轻量详情页入口，详情内包含关系、时间线和证据链入口；原列表仍承载新增、编辑、删除、筛选、分页等高频操作。

理由：当前路线已经多次暴露“工作台层压低表格”的问题。详情抽屉能在不重排首屏结构的前提下承载对象上下文，避免继续把大块关系信息堆到列表上方。

替代方案：每个列表页新增全宽关系图。该方案视觉和数据成本都高，且容易再次压低列表主任务。

### Decision 4: 治理任务中心只表达“可处理待办”，不替代后端事实源和审计系统

选择：任务模型至少包含任务类型、严重级别、影响对象、来源口径、建议动作、处理状态、证据入口和安全边界。P0 处理状态可为前端会话内筛选/忽略/跳转，不承诺持久化；P1/P2 再引入只读聚合接口和持久化状态。

理由：管理员需要“下一步做什么”，而不是只看到指标。先将各页面已能识别的风险变成待办队列，可以提升治理闭环，但不能在没有后端事实源时宣称全局风险已被发现或已处理。

替代方案：只在总览增加风险卡。该方案仍停留在摘要层，无法支持筛选、严重级别、对象影响和处理状态。

### Decision 5: 接入向导采用“预检优先、启用前检查”的安全流程

选择：认证源、应用接入和 Gateway/LLM AI 映射向导统一分为选择对象、填写/核对配置、预检、测试连接或只读模拟、启用前检查、结果页。P0 测试连接可先限定为前端/只读预检和配置完整度检查；真实网络探测、OAuth 回调和 Gateway 发布必须作为后续受控 change。

理由：接入流程天然高风险，必须让管理员先看到缺项、风险和证据。P0 不需要真实认证链路改造，也能减少配置错误。

替代方案：直接在编辑页增加更多表单字段。该方案不能表达分步预检、失败恢复和结果证据，也难以复用到不同接入域。

## Phasing

### P0: 体验层骨架和当前视图只读事实

- 身份资产关系层：从应用、用户、Provider、Agent/Gateway 映射等高价值对象开始，提供详情抽屉、关系列表、证据入口和当前视图来源标签。
- 治理任务中心：提供只读任务队列页面和任务模型，任务候选来自当前列表/当前筛选/已有页面摘要，所有任务标明来源范围和跳转动作。
- 接入体验层：提供向导壳层、预检清单、启用前检查和结果页；测试连接在 P0 表达为配置完整度和只读模拟，不调用真实 OAuth/OIDC 回调或 Gateway 发布。
- 验收：后续 implementation change 必须包含 TS/TSX 类型检查、聚焦测试、构建和浏览器验证，且确认核心列表不被新增体验压到首屏外。

### P1: 只读聚合接口和跨域证据

- 新增只读聚合接口返回对象关系、任务汇总、证据链和 preflight 结果。
- 每个接口必须包含 scope、generatedAt、sourceOfTruth、redactionSummary 和 cannotInfer reason，避免调用方把局部事实误解为全局事实。
- API 不写入任务状态、不执行认证、不触发同步、不触发 Gateway projection publish。

### P2: 处理状态、历史和跨域结果页

- 在明确数据 owner 和审计策略后，再考虑治理任务处理状态持久化、向导历史、测试连接历史和跨域结果证据。
- P2 需要单独定义权限、审计、保留周期、脱敏导出和回滚策略。

## Risks / Trade-offs

- [Risk] P0 从前端当前列表推导任务或关系，容易被误解为全局事实 -> Mitigation: UI、spec 和测试必须显示来源范围，使用“当前视图/当前筛选/只读核对”，需要全局事实时只引用后续只读聚合接口。
- [Risk] 新增详情/任务/向导会再次压低列表主任务 -> Mitigation: 入口优先放在行操作、抽屉、侧栏或独立页面，不在列表上方堆叠大块卡片；浏览器验证记录首屏任务位置。
- [Risk] 接入向导的“测试连接”可能被误实现为真实认证或 Gateway 发布 -> Mitigation: P0 明确为配置完整度和只读模拟；真实探测必须另开受控 change，并记录权限、审计和脱敏策略。
- [Risk] 多个对象关系跨后端事实源，P1 聚合接口可能出现权限和性能问题 -> Mitigation: 先按对象和组织 scope 拆小接口，返回分页/摘要和 cannotInfer，不一次性加载全量组织树或完整审计 payload。
- [Risk] 治理任务中心可能变成静态风险列表 -> Mitigation: 任务模型必须包含影响对象、证据入口、建议动作和处理状态；没有可操作动作的项展示为证据提示而不是待办。

## Migration Plan

1. P0 implementation change 先新增前端类型、详情抽屉/任务队列/向导壳层和聚焦测试，不改真实认证、同步或 Gateway 执行链路。
2. P0 验证通过后，再以独立 change 为高价值对象补只读聚合接口，例如应用接入完整度、Provider 绑定风险、Gateway mapping readiness 或审计证据链。
3. P1 接口稳定后，逐步将 P0 当前视图推导替换为后端只读聚合结果，并保留来源标签。
4. P2 在 owner 明确后再引入持久处理状态、向导历史和测试连接历史。

Rollback 策略：P0 主要为前端体验入口，可通过隐藏入口或回退路由接入点恢复既有列表；P1/P2 接口必须保持只读和向后兼容，失败时 UI 回落到当前视图提示和既有页面。

## Open Questions

- P1 只读聚合接口优先由 Admin 后端统一提供，还是先按应用接入、认证源、Gateway mapping 各自提供小接口，需要后续 implementation owner 决策。
- 治理任务处理状态是否需要持久化、是否纳入审计记录、保存多久，属于 P2 数据治理决策。
- 真实连接测试的授权边界和审计策略需要单独 change 定义，P0 不执行真实 OAuth/OIDC 回调、Provider 登录或 Gateway 发布。
